### 兩項「失敗」的判讀

**第 2 項不是產品缺陷，是驗證程式的斷言基於錯誤前提。** 斷言寫成「LocalMachine 密文無法以 `DataProtectionScope.CurrentUser` 解開」，實測可以解開。這是 Windows DPAPI 的已知行為——`CryptUnprotectData` 解密時不使用 scope 旗標，密文本身記錄了該用哪把主金鑰，因此 .NET 的 `DataProtectionScope` 參數在 `Unprotect` 上沒有區辨作用。原意「確認其未使用使用者範圍」**無法**用這個方法證明。真正有意義的證明是「SYSTEM 能解開管理員加密的資料」，也就是下方需人工執行的端對端排程測試。程式碼確實傳入 `DataProtectionScope.LocalMachine`（`MachineScopedCredentialStorage`），這點已由閱讀原始碼確認。

**第 7 項同樣是斷言寫錯。** 產品行為正確：它拋出 `CredentialStorageException` 並附上「The password was NOT saved.」，而驗證程式卻斷言應成功往返。附帶發現一個真實且合理的行為——非管理員身分執行時，`EnsureRestrictedDirectory` 會建出一個自己也寫不進去的目錄（ACL 只給 Administrators/SYSTEM），隨即明確報錯。這符合設計（`profile set` 本就應以管理員執行），錯誤訊息亦清楚。

### 剩餘項目的執行方式（需管理員權限 + PostgreSQL）

前置：安裝 PostgreSQL 客戶端工具（`winget install PostgreSQL.PostgreSQL`），準備一個可連線的執行個體，並以**系統管理員**身分開啟終端機。

```powershell
# 1. 錯誤密碼應被拒絕儲存（於提示時故意輸入錯誤密碼）
pgbackup profile set --name "verify" -H localhost -d postgres -u postgres
#    預期：退出碼非零、輸出「連線驗證失敗，連線設定並未儲存」

# 2. 正確密碼應通過並儲存
pgbackup profile set --name "verify" -H localhost -d postgres -u postgres
pgbackup profile list          # 應顯示 verify，密碼狀態「已設定」，且無權限警告

# 3. 端對端：以 SYSTEM 身分執行排程任務並完成一次真實備份
schtasks /Create /TN "PostgresBackup_Verify" /TR `
  "pgbackup backup --profile verify -o C:\Temp\pgbackup-verify" `
  /SC ONCE /ST 23:59 /RU SYSTEM /RL HIGHEST /F
schtasks /Run /TN "PostgresBackup_Verify"
schtasks /Query /TN "PostgresBackup_Verify" /V /FO LIST   # 檢查 Last Result 應為 0
dir C:\Temp\pgbackup-verify                                # 應有備份檔產出

# 清理
schtasks /Delete /TN "PostgresBackup_Verify" /F
pgbackup profile remove --name "verify"
```

第 3 項是本次變更的核心使用情境，也是唯一能真正證明「SYSTEM 讀得到管理員建立的機器範圍連線設定」的測試——**在它通過之前，本功能的核心主張未經實地驗證。**

另注意：`EnsureRestrictedDirectory` 現在對既有目錄也會套用權限，但**擁有者仍保有變更權限的能力**，因此 `profile set` 對「目錄已存在且權限不符」改採拒絕而非自動收緊（見票 11）。實機驗證時若 `C:\ProgramData\PostgresBackup` 已存在，請先確認其來歷與權限。
