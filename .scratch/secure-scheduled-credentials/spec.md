# Spec：CLI 機器範圍連線設定與排程憑證安全化

Status: ready-for-agent
> 來源：2026-09-19 設計訪談（grilling + domain-modeling）

## Problem Statement

使用者想要用 Windows 工作排程器做無人值守的自動備份。目前 `docs/USER_MANUAL.md` 提供的排程腳本範例，把 PostgreSQL 的密碼以明碼寫死在腳本參數裡（`$Password = "YourPassword123!"`），再透過 `-p` 交給 CLI。這造成三個實際問題：

1. **密碼明文落在腳本檔案裡。** 任何能讀取該腳本的人（或誤把腳本簽入版控的人）就取得了資料庫密碼。這在多數組織的資安規範下無法通過稽核。

2. **密碼會暴露在行程資訊中。** `-p` 傳入的密碼會出現在 `pgbackup.exe` 自己的命令列上，同一台機器上的任何使用者都能透過工作管理員或 `Get-CimInstance Win32_Process` 讀到；同時也會留在 PowerShell 的歷史紀錄檔中。

3. **文件對外做出了做不到的承諾。** `README.md` 宣稱「No plaintext credentials」，`USER_MANUAL.md` 更直接把 `-p` 描述為「安全環境變數傳遞」——但 `-p` 本身就是暴露面。文件與範例互相矛盾，讀者無從判斷哪個才是正確做法。

CLI 其實已經有 `--profile` 可以讀取已儲存的連線設定，完全不需要 `-p`。但這條路在排程情境下走不通：連線設定與密碼都儲存在**使用者帳號範圍**內（`%APPDATA%` 與該帳號的 Windows 認證管理員），而排程任務通常以其他身分執行。

使用者無法在其環境中建立專用服務帳號，且其個人管理員帳號每三個月強制更換密碼——用個人帳號執行排程會導致任務在換密碼後**靜默停止執行**。因此排程必須以 `SYSTEM` 身分執行，而 `SYSTEM` 看不到使用者以圖形介面建立的任何連線設定。

此外，經稽核發現三個既有的可靠性缺陷會讓上述安全做法在現場**無聲失效**：

- 憑證寫入失敗時，密碼會被靜默保留在行程記憶體的明文字典中，呼叫端仍收到「成功」。程式關閉後密碼消失，使用者毫不知情。
- `--profile` 指定不存在的名稱時，備份作業只印一行警告便繼續執行，還原作業則完全不吭聲。
- `check-tools` 指令不支援 `--profile`，是唯一只能以明文密碼呼叫的指令。

（附帶結論：圖形介面本身的連線設定儲存**沒有洩漏問題**。密碼不寫入設定檔，而是交由 Windows 認證管理員保管，且已有測試釘住此不變條件。本 spec 不改變圖形介面的儲存機制。）

## Solution

為命令列介面建立一套**獨立於圖形介面**的連線設定存放機制，其密碼採用**機器範圍加密**保護，使得以 `SYSTEM` 身分執行的排程任務能夠讀取，而排程腳本中不需要出現任何密碼。

使用者的完整操作流程簡化為：

1. 以系統管理員身分開啟命令列，執行一次 `pgbackup profile set`，以遮蔽輸入的方式打一次密碼。系統會先實際連線驗證帳密正確，才寫入。
2. 排程腳本只需寫 `--profile <名稱>`，腳本中不含任何憑證。
3. 需要更換資料庫密碼時，重跑一次 `pgbackup profile set` 即可。
4. 隨時可用 `pgbackup profile list` 檢視目前有哪些設定、密碼是否正常、存放區權限是否安全。

**安全性定位（必須誠實記載於文件）**：加密採用 Windows 資料保護 API 的機器範圍，代表加密檔**只能在該台機器上解開**，複製到其他電腦即為無效資料。存放區的檔案權限限定為系統管理員與 `SYSTEM`，因此同機的一般使用者無法讀取。但**具備系統管理員權限者可以解開此檔案**——此威脅不在防護範圍內，並將明確寫入文件。此定位已與使用者確認。

同時修正上述三個可靠性缺陷、補齊 `check-tools` 的 `--profile`，並全面改寫文件使其與實際行為一致。

## User Stories

### 建立與管理命令列連線設定

1. 作為系統管理員，我想要用一個指令建立 CLI 專用的連線設定並以遮蔽方式輸入密碼，這樣我就不必把密碼寫在任何檔案裡。
2. 作為系統管理員，我想要在建立連線設定時系統先實際連線驗證一次，這樣我能在當場就發現帳號密碼打錯，而不是等到半夜排程失敗。
3. 作為系統管理員，當資料庫暫時關機或防火牆未開通時，我想要能以明確的強制參數略過驗證先把設定建好，這樣我不必為了建立設定而臨時更動資料庫的可用性或權限。
4. 作為系統管理員，當我使用強制參數略過驗證時，我想要看到明顯的警告，這樣我知道這份設定尚未被證實可用。
5. 作為部署工程師，我想要能以管線方式從標準輸入提供密碼，這樣我可以把「建立連線設定」這一步也納入自動化部署，而不必退回使用不安全的命令列參數。
6. 作為系統管理員，我想要用一個指令列出目前所有的命令列連線設定，這樣我能確認排程會用到的設定確實存在。
7. 作為系統管理員，我想要在列表中看到每筆設定的密碼狀態（已設定／遺失），這樣我能事先發現哪一份設定會在排程執行時失敗。
8. 作為資安稽核人員，我想要確認列表指令在任何情況下都不顯示密碼內容或其任何線索，這樣我能確信此工具不會成為憑證外洩管道。
9. 作為系統管理員，我想要用一個指令刪除連線設定，並確保其加密密碼一併被清除，這樣不會留下孤兒憑證。
10. 作為系統管理員，我想要以相同名稱重新執行建立指令來更新既有設定，這樣更換資料庫密碼時流程一致且直覺。
11. 作為系統管理員，我想要在列表中看到存放區的檔案權限是否仍然安全，這樣若有人不慎放寬了資料夾權限，我能及時發現。

### 排程執行

12. 作為系統管理員，我想要排程腳本完全不含任何資料庫憑證，這樣腳本可以安全地放在共用位置、甚至簽入版控。
13. 作為系統管理員，我想要以 `SYSTEM` 身分執行排程任務，這樣任務不會因為我每三個月更換 Windows 密碼而停止運作。
14. 作為系統管理員，當排程腳本指定了不存在的連線設定時，我想要指令立即以非零代碼失敗，這樣我的腳本錯誤處理能捕捉到它，而不是安靜地持續失敗數個月。
15. 作為系統管理員，我想要文件清楚說明如何以 `SYSTEM` 身分註冊排程任務，這樣我不需要自己摸索工作排程器的執行身分設定。
16. 作為系統管理員，我想要文件說明為什麼不建議用個人帳號執行排程，這樣我理解這個選擇背後的原因而不只是照做。
17. 作為系統管理員，我想要備份失敗時排程腳本以非零代碼結束，這樣工作排程器的執行結果會記錄為失敗，我能從排程器介面察覺異常。

### 憑證儲存可靠性

18. 作為圖形介面使用者，當密碼無法寫入 Windows 認證管理員時，我想要立即看到明確的錯誤，這樣我不會誤以為已經儲存成功。
19. 作為系統管理員，當命令列密碼無法寫入加密存放區時，我想要指令以非零代碼失敗並說明原因，這樣自動化流程能偵測到問題。
20. 作為系統管理員，我不希望密碼在任何情況下被靜默保留為行程記憶體中的明文，這樣可以降低記憶體被傾印時的暴露風險。

### 連線檢查

21. 作為系統管理員，我想要健檢指令也能使用已儲存的連線設定，這樣我檢查客戶端工具版本相容性時不必打出明文密碼。
22. 作為系統管理員，我想要健檢指令的說明文件不再示範以明文密碼呼叫，這樣我不會在無意間學到不安全的用法。

### 兩套連線設定的區隔

23. 作為使用者，我想要圖形介面與命令列的連線設定彼此完全獨立，這樣兩者的行為可預測，不會出現「刪掉了卻還在」的困惑。
24. 作為圖形介面使用者，我想要在連線設定畫面看到一行說明，告知此處的設定不供排程使用，這樣我不會在排程失敗時困惑於「我明明建好了」。
25. 作為使用者，我想要列表指令標示每筆設定的來源，這樣我一眼就能分辨自己在看哪一套。

### 文件與稽核

26. 作為資安稽核人員，我想要有一節專門的安全性說明，清楚交代密碼儲存在哪裡、誰讀得到、以及明確不防護哪些對象，這樣我不必自行翻找拼湊。
27. 作為讀者，我想要文件中所有關於密碼安全的敘述都與實際行為相符，這樣我能信任這份文件。
28. 作為使用者，我想要文件明確說明 `-p` 參數的暴露風險與適用時機，這樣我知道它只適合手動除錯。
29. 作為使用者，當我在指令中使用 `-p` 時，我想要看到一行執行時警告，這樣即使我沒讀文件也會被提醒。
30. 作為未來的維護者，我想要有一份架構決策記錄說明為何命令列不沿用 Windows 認證管理員，這樣我不會誤以為這是疏忽而擅自「修正」它。
31. 作為未來的維護者，我想要領域詞彙表區分兩種連線設定，這樣討論時不會混淆。

## Implementation Decisions

### 架構：重用既有接縫，不新增儲存抽象

- **`IConnectionProfileRepository` 介面維持不變。** 命令列的新存放機制實作為此介面的第二個實作（機器範圍版本），與既有的使用者範圍實作並存。
- **`ICredentialStorage` 介面維持不變。** 新增一個以 Windows 資料保護 API 機器範圍加密的實作，與既有的 Windows 認證管理員實作並存。
- **兩套設定的獨立性由相依注入決定，而非由程式邏輯決定。** 命令列進入點註冊機器範圍實作，圖形介面進入點註冊使用者範圍實作。兩邊在執行期完全看不到對方的資料，不需要任何額外的隔離機制或查找順序邏輯。
- 此決定使 `--profile` 在備份作業、還原作業與健檢指令上完全不需要修改查找邏輯。

### 命令列連線設定存放區

- 存放位置為機器層級的共用應用程式資料目錄下的 `PostgresBackup` 資料夾，檔名刻意與圖形介面的設定檔不同，以避免混淆。
- 存放區必須位於機器層級而非使用者層級，否則以 `SYSTEM` 身分執行的排程任務無法讀取。
- 存放區建立時即套用限制性檔案權限，僅允許系統管理員群組與 `SYSTEM` 讀寫。
- 連線設定的非機密欄位（名稱、主機、連接埠、資料庫、使用者名稱、建立時間）以明文 JSON 儲存；密碼單獨以機器範圍加密後儲存。
- 密碼加密採用 Windows 資料保護 API 的機器範圍。這需要引入 `System.Security.Cryptography.ProtectedData` 套件，為本次唯一的新依賴。
- 機器範圍的安全性語意須明確記載：加密結果與機器綁定，複製至他機無效；同機的低權限使用者受檔案權限阻擋；同機的系統管理員可解密，此為已接受的風險。

### 新增的命令列指令

- 新增 `profile` 指令群組，包含三個子指令：建立／更新、列出、刪除。
- **建立／更新**：接受連線參數與設定名稱。密碼預設以互動式遮蔽輸入取得；另支援從標準輸入讀取密碼，供自動化使用。**不提供**以命令列參數傳入密碼的選項——在新功能中重新製造正在修復的問題是不可接受的。
- **建立／更新**預設會實際連線驗證帳密，驗證失敗則**拒絕儲存**。提供一個必須明確指定的強制參數以略過驗證，使用時印出明顯警告。
- 相同名稱視為更新，覆寫既有設定。
- **列出**：顯示名稱、主機與連接埠、資料庫、使用者名稱、來源標示、建立時間，以及密碼狀態（已設定／遺失）。密碼狀態僅呈現有無，不呈現任何內容或長度。
- **列出**同時檢查存放區的檔案權限是否仍符合預期，不符則印出警告。
- **刪除**：移除設定項目並一併清除其加密密碼。

### 檔案權限檢查的接縫位置

- 檔案權限檢查方法加入既有的 `IEnvironmentProbe` 介面。該介面的既有職責即為「探測作業系統環境（檔案系統、環境變數、常見路徑、Registry）」，權限查詢屬於同一類職責。
- 明確**不**將此方法加入 `IConnectionProfileRepository`：那會強迫圖形介面的實作也實作一個它永遠用不到的方法，讓命令列專屬需求污染共用介面。
- 權限檢查僅在建立／更新與列出時執行，備份作業與還原作業執行時**不**檢查。理由：每次備份都檢查只會在排程記錄中重複產生相同警告，長期下來無人閱讀；放在使用者主動查詢狀態的指令中最可能被真正看見。

### 密碼輸入接縫

- 新增 `IPasswordReader` 接縫，封裝互動式遮蔽輸入與標準輸入讀取兩種來源。這是本次唯一新增的接縫，理由是直接操作主控台無法在測試中驗證。
- 接縫應置於盡可能高的位置：由命令列層取得密碼字串後傳入既有的儲存介面，而非讓儲存層自行讀取輸入。

### 既有行為修正

- **憑證寫入失敗改為明確失敗。** 移除寫入失敗時靜默退回行程記憶體明文字典的行為；在 Windows 上寫入失敗即拋出例外，由呼叫端呈現錯誤。記憶體儲存路徑僅保留給非 Windows 平台與測試（需由明確旗標開啟）。
- **`--profile` 找不到指定設定時改為錯誤退出。** 備份作業目前印警告後繼續、還原作業目前完全靜默，兩者統一改為以非零代碼結束。理由：使用者明確指定了設定名稱，找不到即為設定錯誤，沒有理由假裝可以繼續。
- **健檢指令補上 `--profile`**，行為與備份作業、還原作業一致。
- **`--connection-string` 予以保留**，但在說明文字與文件中標註僅供互動式除錯使用，不得用於排程腳本。
- **`-p` 參數予以保留**，但使用時印出一行執行時警告，說明其密碼會暴露於行程資訊中。保留的理由是移除屬破壞性變更，且手動除錯時確有價值；加上警告是為了讓僅閱讀 `--help` 而未讀文件的使用者也能得知風險。

### 圖形介面的變更

- 圖形介面的連線設定儲存機制**不做任何改變**。經稽核確認其無洩漏問題。
- 連線設定畫面新增一行說明文字，告知此處設定僅供本程式使用，排程與命令列請另行以 `profile` 指令建立，並指向使用手冊。
- 圖形介面**不**顯示命令列的連線設定清單。那會使圖形介面重新讀取命令列的存放區，抵銷剛建立的獨立性。

### 文件變更

- 改寫使用手冊的排程腳本範例，移除所有密碼相關參數，改用 `--profile`。
- 新增以 `SYSTEM` 身分註冊排程任務的操作說明，並說明為何不建議使用個人帳號（Windows 密碼到期會導致任務靜默停止）。
- 新增 `profile` 指令群組的完整參數說明與使用範例，包含從標準輸入提供密碼的自動化用法。
- 修正三處與事實不符的敘述：README 的「無明文憑證」宣稱、手冊中將 `-p` 描述為「安全環境變數傳遞」的錯誤敘述、以及常見問題中關於命令列串接的不精確說明。
- 移除 README 中「圖形介面建立的連線設定可立即透過命令列使用」的承諾——此承諾在本次變更後不再成立。
- 於使用手冊新增獨立的「安全性說明」一節，內容涵蓋：兩套連線設定各自存放於何處、分別由誰可讀取、加密的實際保護範圍、以及明確不防護的對象。**此節必須以一般讀者能理解的語言撰寫，避免堆砌術語。** README 僅放一段摘要並連結至此節。
- **不**新增 `SECURITY.md`：該檔名在開源慣例中用於漏洞回報流程，放置此內容會造成誤導。

### 記錄

- 新增一份架構決策記錄，說明「命令列採用機器範圍加密存放區、與圖形介面連線設定完全獨立」此一決定及其取捨，包含已評估但未採用的方案（以 `SYSTEM` 身分寫入 Windows 認證管理員、改用 Windows 整合驗證免除密碼）與未採用的理由。此決定符合記錄門檻：難以回頭（存放格式一旦被使用即固定）、不看背景會令人不解（為何放著現成的認證管理員不用）、且為真實權衡的結果。

## Testing Decisions

### 好的測試的標準

只驗證外部可觀察的行為，不驗證實作細節。對命令列而言，可觀察的行為是**退出碼**與**輸出內容**；對儲存層而言，是**存進去的能否取出**以及**機密是否確實不出現在非機密的持久化內容中**。測試不應斷言私有方法被呼叫、不應斷言內部資料結構的形狀。

### 既有測試的前例

- 命令列指令測試沿用備份指令測試的既有模式：以 Moq 建立各服務接縫的替身、註冊至相依注入容器、組出根指令、以引數陣列解析並執行、斷言退出碼。
- 儲存層測試沿用連線設定倉儲測試的既有模式：指定測試用檔案路徑、寫入後讀回、並斷言持久化檔案內容中不包含密碼字串。

### 自動化測試範圍（簽入版控）

- **`profile` 指令群組**：建立／更新在驗證成功時退出碼為零；驗證失敗時拒絕儲存且退出碼非零；指定強制參數時即使驗證失敗仍儲存且輸出包含警告；列出指令的輸出包含設定名稱與密碼狀態且**不包含密碼字串**；刪除指令移除項目後列出指令不再顯示該項目。
- **密碼輸入接縫**：從標準輸入讀取時正確取得密碼；密碼不出現在任何輸出中。
- **機器範圍存放區實作**（以檔案路徑注入的方式測試其非加密部分）：非機密欄位正確持久化；**持久化檔案內容不包含密碼字串**——此為核心不變條件，須明確斷言。
- **`--profile` 找不到設定的行為**：備份作業與還原作業在指定不存在的設定名稱時，退出碼均為非零。
- **健檢指令的 `--profile`**：能取得已儲存的連線設定並成功執行。
- **憑證寫入失敗的行為**：寫入失敗時拋出例外而非靜默成功；記憶體儲存路徑僅在明確旗標開啟時生效。
- **`-p` 的執行時警告**：使用該參數時輸出包含警告文字。

### 整合測試範圍（必須實際執行，但不得簽入版控）

以下路徑無法以替身驗證，必須在真實環境中實際執行一次並確認通過，但因其依賴特定機器狀態、系統管理員權限與實際的 PostgreSQL 執行個體，**不得簽入版控**（會導致持續整合環境失敗）：

- **真實的機器範圍加密與解密往返**：以資料保護 API 實際加密後解密取回相同密碼。
- **加密結果的機器綁定性質**：確認加密輸出無法在其他機器上解開（或至少確認其未使用使用者範圍）。
- **真實的檔案權限套用與檢查**：存放區建立後其權限確實限定於系統管理員與 `SYSTEM`；人為放寬權限後，列出指令確實印出警告。

  **例外（票 11 後追加）：** `MachineScopedStoreRestrictedDirectoryTests` 確實套用真實的存取控制清單，但**簽入版控**。它與上述禁令的差別在於：它只在自建的暫存目錄上操作，從不觸及真實的機器層級存放區，也不需要系統管理員權限；在無權變更存取控制清單的環境下會條件式略過，而非讓斷言在毫無驗證力的情況下通過。它釘住的是票 11 那個已實測確認的漏洞——「搶先建立的目錄必須也被收緊」——若不簽入，本批變更中最重要的安全修正就完全沒有防線。本節禁止的是「依賴特定機器狀態或系統管理員權限、會讓持續整合失敗」的測試，此測試兩者皆非。
- **真實的 Windows 認證管理員寫入路徑**：此路徑目前完全未被覆蓋——既有測試以強制記憶體儲存旗標繞過了它。須實際驗證寫入、讀回、刪除，以及寫入失敗時確實拋出例外。
- **以 `SYSTEM` 身分的端對端排程流程**：以系統管理員身分建立連線設定後，註冊一個以 `SYSTEM` 身分執行的工作排程任務，確認其能讀取該設定並完成一次實際備份作業。此為本次變更的核心使用情境，必須實地驗證。
- **實際連線驗證行為**：對真實 PostgreSQL 執行個體，確認錯誤密碼會被拒絕儲存、正確密碼會通過。

執行結果須回報，但這些測試檔案應置於版控忽略的位置或於驗證後移除。

## Out of Scope

- **不防護具備本機系統管理員權限的對象。** 在 Windows 上任何本機憑證保護機制（資料保護 API、認證管理員）對系統管理員而言皆可解開。將此納入目標會導向需要硬體安全模組或外部憑證保管服務的結論，與本工具的定位不成比例。此界線將明確寫入文件。
- **不修改 PostgreSQL 伺服器設定。** 使用 Windows 整合驗證可以完全免除密碼儲存，在資安上優於任何加密方案，但需要變更伺服器端的連線驗證設定，已確認不在使用者可控範圍內。
- **不移除 `-p` 參數。** 屬破壞性變更，且手動除錯時具實際價值。改以警告與文件處理。
- **不移除 `--connection-string` 參數。** 同上理由。
- **不改變圖形介面的連線設定儲存機制。** 經稽核確認無洩漏問題。
- **不讓圖形介面管理命令列的連線設定。** 兩套設定的獨立性是刻意的設計決定。
- **不建立專用服務帳號相關的自動化。** 使用者環境中無法建立帳號。
- **不處理備份失敗的通知機制**（電子郵件、告警等）。雖與「排程靜默失敗」的主題相關，但屬獨立功能。
- **不處理圖形介面測試連線失敗時例外訊息可能回吐連線字串內容的風險。** 此為稽核中發現的次要項目：測試連線會將含密碼的連線字串交給資料庫驅動程式，連線字串格式錯誤時拋出的例外訊息有可能包含其內容。發生條件狹窄（密碼含特殊字元導致連線字串格式異常），建議另立項目處理。

## Further Notes

- 本專案目前**尚無任何發行標籤**，因此「圖形介面與命令列連線設定完全獨立」這項破壞性變更不會影響既有使用者的腳本，僅需更新文件中的相關承諾。
- 使用者的環境限制是本設計的主要驅動力，應記入架構決策記錄：無法建立專用服務帳號、個人管理員帳號密碼每三個月強制更換、無法變更 PostgreSQL 伺服器設定。這三項限制共同排除了其他所有方案，只剩下「以 `SYSTEM` 執行 + 機器範圍加密存放區」一條路。
- 設計取捨的核心原則：**讓最安全的做法同時也是最省事的做法**。曾評估過「以 `SYSTEM` 身分寫入 Windows 認證管理員」的方案，其安全等級略高，但要求使用者每次更換資料庫密碼時執行一套多步驟的手動儀式。麻煩的安全流程在現實中會被跳過，最終使用者會退回在腳本中寫明文密碼——實際安全性反而更差。
- 稽核中確認為**正確且應予保留**的既有行為：備份作業與還原作業的引數建構器不含密碼；密碼透過子處理序的環境變數傳遞給客戶端工具；備份紀錄中持久化的引數字串不含密碼；圖形介面使用真正的密碼輸入控制項。若日後有人考慮將憑證移入引數字串，須注意該字串會被寫入備份歷史資料庫。
