# 命令列連線設定採用機器範圍加密存放區，與介面連線設定完全獨立

Status: accepted

命令列介面（CLI）需要在以 `SYSTEM` 身分執行的排程任務中讀取資料庫密碼，而圖形介面既有的連線設定儲存於使用者帳號範圍（使用者的 `%APPDATA%` 與該帳號的 Windows 認證管理員），`SYSTEM` 讀不到。我們因此為命令列建立一套獨立的連線設定存放區，密碼以 Windows 資料保護 API 的**機器範圍**加密（而非使用者範圍、也不沿用 Windows 認證管理員），與圖形介面的連線設定在儲存位置與存取路徑上完全不相交。

## 驅動限制

這三項無法變更的環境限制排除了其他所有方案，只留下這一條路：

- 使用者的環境中**無法建立專用服務帳號**，排程只能以既有身分執行。
- 使用者的**個人管理員帳號密碼每三個月強制更換**；若排程以個人帳號執行，換密碼後任務會**靜默停止運作**，因此排程必須以 `SYSTEM` 身分執行。
- **無法變更 PostgreSQL 伺服器的連線驗證設定**，因此無法採用免密碼的驗證方式。

## Considered Options

**1. 以 `SYSTEM` 身分寫入 Windows 認證管理員。**
安全性略高於機器範圍加密（不依賴檔案系統權限，且密碼不落地為檔案）。未採用：`SYSTEM` 帳號的認證管理員憑證與使用者帳號的不共通，要讓 CLI 與排程都能穩定讀寫，需要在每次更換資料庫密碼時執行一套多步驟的手動儀式（以特定身分開啟工具、寫入、驗證）。麻煩的安全流程在現實中會被跳過——使用者最終會退回在腳本裡寫明文密碼，實際安全性反而更差。我們判斷「讓最安全的做法同時也是最省事的做法」比理論上略高的安全等級更重要。

**2. 改用 Windows 整合驗證（Integrated Authentication）以完全免除密碼儲存。**
安全性優於任何加密方案，因為密碼從此不需要儲存。未採用：需要變更 PostgreSQL 伺服器端的連線驗證設定，已確認不在使用者可控範圍內。

**3.（採用）機器範圍加密存放區，與圖形介面連線設定完全獨立。**
密碼以機器範圍加密後與非機密欄位一起存放於機器層級目錄，檔案權限限定管理員與 `SYSTEM`。不需要任何手動換密碼儀式：使用者以系統管理員身分執行一次建立指令即可，機器上的 `SYSTEM` 排程任務即可讀取。兩套連線設定的獨立性由相依注入決定——命令列進入點與圖形介面進入點各自註冊不同的儲存實作，彼此在執行期看不到對方的資料，不需要額外的隔離或查找順序邏輯。

## 已接受的風險

機器範圍加密的解密只需該台機器本身，**任何具備本機系統管理員權限者都能解開此存放區**。此威脅明確不在防護範圍內：Windows 上任何本機憑證保護機制（資料保護 API、認證管理員）對系統管理員而言皆可解開，將防護此對象納入目標會導向需要硬體安全模組或外部憑證保管服務的結論，與本工具的定位不成比例。此風險已與使用者確認並接受。

## Consequences

- 圖形介面建立的連線設定無法直接被命令列使用，反之亦然；這是刻意的設計結果，而非疏忽。
- 加密結果與產生它的機器綁定：存放區檔案複製到另一台機器上即為無效資料，無法解密。
- 一旦命令列連線設定的存放格式開始被實際使用，格式即固定下來——變更格式即為破壞性變更，因此此決定被視為難以回頭。
